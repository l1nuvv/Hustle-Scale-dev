# Hustle and Scale — инженерный стандарт разработки

**Версия:** 1.0.1, 18.10.2026, с локальным уточнением состояния проекта. **Статус:** интегрировано локально; не опубликовано в GitHub.

**Область:** Unity, C#, архитектура, качество, инструменты, системный/игровой дизайн.

**Порядок производства, 20.10.2026:** [DEVELOPMENT_PLAN.md](DEVELOPMENT_PLAN.md) задаёт этапы и условия перехода. Сначала проверяется полный цикл в компактном районе, затем принимается вертикальный срез и расширяется игра. Этот стандарт задаёт технические решения внутри выбранного этапа; он не требует строить все системы заранее.
**Приоритет:** утверждённый FIRST DEAL определяет правила отдельного сценария; городские решения S1/E6 описаны в [CITY_GAMEPLAY](CITY_GAMEPLAY.md), их нельзя заменять правилами смены FIRST DEAL; фактический checkout + Editor определяют техническую реальность. Этот документ не изменяет GDD, не утверждает апгрейд движка и не даёт агенту права на коммиты/push.

**Исходное состояние, 18.10.2026:** Unity 6000.6.0f1, манифесты пакетов, настройки и метаданные приняты и закоммичены. Следующая миграция требует отдельной задачи.

## 1. Цель и критерии выбора технологии

Строить современную, **поддерживаемую одним разработчиком** игру, в которой можно безопасно добавить новые товары, сделки, NPC и инструменты, не переписывая существующий цикл. Современность означает актуальную поддерживаемую версию, документированный API, хорошую диагностику и испытанную полезность, а не максимальный номер языка, число абстракций или сторонних пакетов.

Для нового инструмента/паттерна ответить: (1) какая конкретная проблема решается сейчас, (2) что проще из штатных средств Unity, (3) как проверить пользу и совместимость, (4) кто будет сопровождать код. Без ответов не внедрять.

## 3. Современный C#: использовать по назначению

**Предпочтительные приёмы:** `readonly` и ограничение изменяемости там, где это сохраняет инварианты; `enum`, `switch` expressions, pattern matching, null-conditional access, explicit value objects для ID/денег/времени при реальной пользе; небольшие методы с явным результатом и проверкой предусловий; `Try...`-операции или компактный `Result` для операций с несколькими ожидаемыми причинами отказа; интерфейсы **на границах** с несколькими реализациями (например, часы в тестах), не для каждого класса.

**Денежные расчёты:** суммы FIRST DEAL целочисленные в долларах, хранить `int`/`long`, без `float`/`double`, округлений и разных копий баланса в UI. Когда появятся центы — целочисленные минимальные единицы валюты. `decimal` допустим в чистых вычислениях при обоснованной необходимости, но **не** полагаться на штатную сериализацию `decimal` Unity. Отрицательные/переполненные суммы проверять на границах операций.

**Состояние и сериализация:** разделять Authoring-конфигурацию, runtime-данные и DTO существующих городских сохранений. В Inspector — `[SerializeField] private` для ссылок и настроек; public API — через свойства/методы. Не исходить из того, что Unity сериализует auto-properties, `readonly`-поля, полиморфные интерфейсы или все коллекции одинаково между версиями. `[SerializeReference]` — только при реальной необходимости полиморфных сериализованных объектов. `record`/`init`/`IsExternalInit` **не применять к сериализованным моделям Unity**; `init` не является готовой штатной возможностью этой Unity. Возможности словарей в новых версиях проверять на фактической версии, не переделывать старые assets ради новинки.

**Асинхронность:** обычный геймплей, анимации и задержка ремонта — Unity Update/Coroutine/контролируемые игровые часы; `async/await` нужен только для настоящего I/O. Нельзя вызывать Unity API из `Task.Run`/постороннего потока. Не использовать `async void` для игровой бизнес-логики, fire-and-forget без обработки ошибок или `CancellationToken` без жизненного цикла.

**Горячие пути:** не аллоцировать мусор в каждом `Update` без причины, не полагаться на постоянные `FindObjectOfType`/глобальный поиск, не подписываться на события многократно. Оптимизировать только измеренный Profiler-ом участок. Burst/Jobs — по профилю CPU, **не по привычке**.

## 4. Архитектура FIRST DEAL — простая, но с границами

```text
Unity Input / Camera / raycast / world objects
               |
      Interaction Adapter (MonoBehaviour)
               |
    Application use cases / operations
   (PurchaseLot, Inspect, Repair, Deliver)
               |
  Domain state + invariants (plain C#)
 (ItemInstance, Wallet, Order, GameClock)
               |
     Read-only presentation state
          HUD / prompts / feedback
```

Схема описывает **ответственности**, а не требование создавать 5 сборок и классы с каждым из этих имен. `MonoBehaviour` отвечает за сцены, ссылки, physics, ввод и визуальный feedback; **не определяет прибыль, допустимость сделки или состояние заказа**. Чистые C#-объекты отвечают за правила, ID экземпляров, деньги и переходы состояний. UI не меняет Domain напрямую. ScriptableObject хранит **статические настройки** товара, станции или заказов, а не текущий баланс и владельцев.

**Первый слой ответственности:**
- `FlashlightUnit` / item instance: `InstanceId`, фактическое состояние, известный результат проверки, местоположение; один экземпляр не может существовать в двух местах.
- `Wallet`: деньги и строго проверяемые списания/зачисления. Нет отрицательного баланса.
- `Order`: допустимые статусы и требования, дедлайн, однократное исполнение.
- `GameClock`: единый источник elapsed-time, старт/пауза, граничные условия. Для FIRST DEAL A=`09:00` и B=`18:00` означают **9 и 18 минут от запуска игрового таймера**, не время суток. Ремонт добавляет 240 игровых секунд сразу, а не требует четырёх минут реального ожидания. В городе сроки А/Б отсчитываются от принятия каждого заказа.
- Операция сделки: валидирует **все** предусловия, затем меняет заказ, владельцев и деньги согласованно. Нет частичных списаний и повторной оплаты. Возвращает явную причину отказа.
- Unity-адаптер: получил `E`/наведение, вызвал конкретную операцию, отобразил результат. Не поддерживать параллельный автоподбор через старые trigger-пути.

Сборка зависимостей — простая композиция на сцене через Inspector/явное создание runtime-классов в одном месте. Не требуются ServiceLocator, global singleton, контейнер DI, тяжёлые слои DDD или универсальные `Manager`-классы. **Интерфейс вводить для реальной границы/замены в тестах**, не ради имитации enterprise-архитектуры.

**Модули / папки (ориентир, не команда массового переноса):** `Gameplay/Items`, `Gameplay/Economy`, `Gameplay/Orders`, `Gameplay/Time`, `Gameplay/Interactions`, `UI`, `Tests`. Оставлять пригодные существующие файлы на месте, пока перенос не решает проблему. Assembly Definition использовать умеренно (например, Domain + Tests), когда тестам нужен отдельный модуль или это реально уменьшает зависимости/время компиляции; сначала проверить текущие asmdef, не создавать их автоматически.

## 5. Паттерны: когда применять, когда не надо

| Паттерн / принцип | Конкретное применение | Решение |
|---|---|---|
| **Composition over inheritance** | Поведение продаваемого объекта складывается из компонентов и данных, а не иерархии из десятков видов фонарей | **Применять** |
| **State machine / explicit transitions** | `Available -> Accepted -> Completed` или `Expired`; граница дедлайна | **Применять** в доменных переходах, без универсальной FSM-библиотеки |
| **Command / use-case method** | `TryPurchaseLot`, `TryRepair`, `TryDeliverOrder`: одна команда — один валидируемый итог | **Применять** как обычные методы/классы без command bus |
| **Observer** | Событие «деньги/заказ изменены» обновляет HUD, который не владеет данными | **Локальные C# events** либо явный refresh; не EventBus |
| **Strategy** | Позднее действительно разные правила оценки/ценообразования, заменяемые без ветвления на десятки типов | **Отложить**; один FIRST DEAL не требует стратегий |
| **Factory** | Если появится несколько способов корректно создавать экземпляры с валидными ID и состояниями | **По необходимости**; не для трёх заранее заданных фонарей |
| **Data-driven design** | Настраиваемые цены, длительности, требования; конфиги доступны дизайнеру в Inspector и валидируются | **Пригодно**, без общего скриптового языка правил |
| **SOLID** | Разделение ответственности, короткие зависимости, подмена clock в тестах | **Прагматично**, не максимизировать число интерфейсов |
| **ECS/DOTS, CQRS, Event Sourcing, Repository/UoW, DI framework, microservices** | Нет оправдывающей нагрузки/масштаба в 3 товарах и 2 заказах | **Не вводить** |

## 6. Системный дизайн и геймдизайн как инженерные требования

**Главная проверка FIRST DEAL:** интересно ли принимать решение под дефицитом товара, времени и денег, а не просто нажимать `E`. Система должна делать **информацию, действие и последствия** понятными.

1. **Game loop:** получить информацию → оценить две конкурирующие возможности → проверить и при необходимости починить товар → выбрать обязательство → физически передать → увидеть деньги, остаток, последствия и следующую возможность. Все звенья должны реально работать в Play Mode.
2. **Дилемма вместо рутины:** ограниченный запас (3 единицы) конкурирует с требованиями покупателей; ремонт стоит $50/4 мин; правила заказов нельзя скрывать за UI. Добавление товара, станции, NPC допустимо только если даёт **новое осмысленное решение**, а не удлиняет перенос предметов.
3. **Affordances / feedback:** подходящий объект подсвечивается или получает короткую подпись; отказ указывает **конкретное условие**; диагностика имеет заметную реакцию в игровом мире; изменение денег и заказов отражается в HUD без двойных источников истины.
4. **Soft-lock prevention:** игрок не должен попасть в непонятный тупик из-за исчерпания вариантов. Подтверждённый FIRST DEAL определяет механизм обратного выкупа; нельзя придумать новые «спасательные» выплаты без согласования.
5. **Тайминг:** отдельно проверить достижимость маршрутов A, B, комбинированного с ремонтом; реалистичные траектории и время на осмотр/перенос, не только арифметику. Дедлайны 09:00/18:00 — elapsed minutes.
6. **Balance:** фиксировать тестовые параметры и результаты 3–5 самостоятельных прохождений. Оценивать: понял ли игрок условие, как быстро выбрал путь, замечал ли альтернативу, где терял время, насколько полезен ремонт, хочется ли повторить. **Не менять утверждённые цены/дедлайны тайно**: предложить корректировку на основе доказательств и согласовать.
7. **Бюджет визуального дизайна:** сначала graybox/читаемые действия, потом единый визуальный язык, материалы, звук; случайные модели из разных паков не являются художественным направлением.

Дизайн-документ описывает гипотезу; только **плейтест** даёт свидетельство об интересности и удобстве. Не заменять удовольствие от игры количеством чистых классов, эффектов или систем.

## 8. Контроль качества и Definition of Done

1. **Перед изменением**: `git status --short`, релевантные исходники + связи сцен/префабов, воспроизводимая проблема, границы задачи.
2. **Архитектурный контроль**: бизнес-правила не в UI/MonoBehaviour; одна единица товара — один ID/владелец; одна сделка — одно начисление; нет новых зависимостей без доказанного выигрыша.
3. **Статическая проверка**: diff review, `git diff --check`, отсутствие случайных `.meta`/GUID-изменений и массового изменения сериализованных assets.
4. **Автотесты (где доступна Unity)**: покупка не дважды, перенос без дублирования, ремонт/повторная диагностика, условие и повтор продажи, недостаток денег, границы дедлайнов, пауза. Domain — EditMode; сценовые интеграции — PlayMode.
5. **Ручной сценарий**: управление/коллизии, фокус/E, 3 фонаря, A/B, ремонт, выбор пути, итоги, обратный выкуп. Отказ объясняется, HUD не расходится с моделью.
6. **Производительность**: сначала проверить видимые тормоза и Profiler; никаких заявлений о «ускорении» без измерения.
7. **Отчёт агента**: что и почему изменено; какие тесты запускались, версии Unity и пакетов, результат; что не проверено, что осталось рискованным. При read-only задачи — никаких изменений.

Тестовый класс/компонент, не используемый в сцене, **не** доказывает рабочий игровой цикл. Изоляция логики и современный синтаксис C# **не** заменяют проверку в Editor/Player и плейтест.

## 9. Существующая реализация и порядок применения

Схема раздела 4 — модель ответственности, не описание реально существующих классов `Wallet`/`GameClock` и не задание их создать. Деньги, предметы и переходы находятся в `Assets/Scripts/Inventory/WorkshopSession.cs` и partial-файлах `WorkshopTrading`, `WorkshopOutcome`, `WorkshopCarrying`, `WorkshopPersistence`. Городские адаптеры — `CityTradeView`/`CitySaveController`; файловое хранение — `CitySaveStore`.

Основное записанное покрытие — редакторские harness из `Assets/Editor/`, запускаемые через Tools. Их assertions не являются количеством NUnit-тестов или независимых игровых сценариев. Test Framework установлен, но наличие пакета не означает, что эти harness запускаются через Test Runner. При проверке выбрать реальный инструмент по затронутой области; текущие меню приведены в ROADMAP и исходниках проверок.

Исторический порядок T01–T06 ниже сохраняет границы исходного сценария. Это не текущая очередь: следующий шаг определяется [ROADMAP](ROADMAP.md#current-status).

- **Текущая интеграция:** стандарт и исходное состояние проекта сохранены в локальных коммитах.
- **T01:** локальная техническая проверка завершена; проверку воспроизводимости из чистого клона проводить отдельно.
- **T02–T05 (история):** реализованы необходимые для FIRST DEAL domain, Unity-адаптеры, сцены, UI и обратная связь. Следовать границам ответственности, но не делать большой «чистый» рефакторинг старого инвентаря вне задачи.
- **T06:** существует harness инвариантов и маршрутов; человеческие наблюдения записаны отдельно в [FIRST DEAL](FIRST_DEAL.md). Не переоткрывать эти работы автоматически.

**Запрещённые автоматические действия:** переход Unity/пакетов на произвольные новейшие версии, введение C# выше поддерживаемого, апгрейд .NET вне Unity, установка новых платных инструментов, переписывание проекта, реорганизация всех папок, CI/DI/сетевая инфраструктура и массовые коммиты ради «модернизации».
