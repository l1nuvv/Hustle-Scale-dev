# План развития Hustle and Scale

Дата: 19.10.2026. Основание: анализ текущего репозитория и обсуждение с владельцем.

Статус: зафиксированный план с рекомендуемым reasoning effort агента по каждой задаче. Фиксация плана не означает разрешение на реализацию всех этапов, изменение правил FIRST DEAL или импорт внешней спецификации. Объём следующей реализации выбирается отдельно.

## 1. Исходное состояние

- В проекте записана Unity 6000.6.0f1; используются URP и Input System. Основная сцена — `Assets/Scenes/FirstDealTrade.unity`.
- Реализована одна смена FIRST DEAL: покупка трёх фонарей, перенос, диагностика, ремонт, заказы со сроками, повторный заказ, обратный выкуп, итоги и перезапуск.
- Состояние предметов и экономика находятся в `WorkshopSession` и его partial-файлах. Старый инвентарь существует отдельно; перед расширением ассортимента нужно определить единую модель владения предметами.
- Есть редакторские проверки T02–T06. README и локальные журналы содержат результаты предыдущих запусков; это не новые проверки в рамках составления плана. В README описано одно ручное прохождение.
- Визуал остаётся прототипным: примитивы, условные персонажи, цветовые ориентиры, крупные текстовые панели. Есть световая реакция диагностики.
- В просмотренном игровом коде не обнаружены сохранения, переход к следующей смене и развитие мастерской.

Основа анализа: код, сериализованная структура сцены, редакторские инструменты, README, журналы и сохранённые скриншоты. Новое прохождение или запуск Unity для этого анализа не выполнялись. Интересность, баланс и самостоятельное освоение ещё требуют наблюдения за игроками.

## 2. Цель и границы

Ближайшая цель — небольшой убедительный игровой фрагмент: понятная первая смена, приятные действия с предметами, цельный образ мастерской и причина продолжить игру.

Проверяемая гипотеза: игроку интересно оценивать товар и выбирать сделки при ограниченных деньгах и времени. После FIRST DEAL проверить её на второй вручную спроектированной смене с тем же товаром.

Предложенное художественное направление: стилизованный приземлённый реализм — мастерская подержанных вещей и небольшой торговый двор. Это предложение, а не утверждённый арт-стандарт.

План ограничен одной компактной локацией, двумя сменами, одним улучшением мастерской и одним дополнительным товаром. Не включает большой город, сотрудников, транспорт, мультиплеер, сложную рыночную симуляцию, обновление Unity/пакетов, платные сервисы, релизную подготовку и упаковку.

## 3. Как читать effort

Effort здесь — рекомендуемый уровень рассуждения агента для отдельной задачи. Это не оценка времени человека, не выбор модели и не автоматическое переключение настройки текущего чата.

| Effort | Когда использовать |
| --- | --- |
| low | Простая локальная правка, обновление фактов, подготовка чек-листа, подключение готовых звуков |
| medium | Уровень по умолчанию: UI, сцена, визуальная интеграция, дизайн небольшой механики |
| high | Сохранения и восстановление состояния, инварианты экономики, общая модель предметов, сложные регрессии |

Правила экономного выполнения:

- Выбирать задачу по ID и начинать с указанного effort. Не запускать весь этап на high из-за одной сложной задачи.
- Повышать effort только для конкретной неразрешённой проблемы: воспроизводимый дефект, неоднозначные переходы состояния, риск потери или дублирования предметов/денег. После её решения возвращаться к обычному уровню.
- Не использовать xhigh/max для текущего плана без отдельно обнаруженной необходимости. Повышенный effort сам по себе не заменяет проверку.
- Читать только затронутые файлы и уже подтверждённые зависимости. Не повторять полный аудит и не перечитывать весь план на каждой задаче.
- Делать одну небольшую законченную задачу; запускать подходящие узкие проверки один раз, повторять после изменений или при сбое. Обязательные проверки не сокращать.
- Не создавать агентов, архивы, сборки, новые документы или инфраструктуру без потребности текущей задачи. Обновлять существующие документы.
- G2 требует реальных игроков: агент с low готовит и сводит наблюдения, но не заменяет человеческое прохождение. Художественные задачи требуют просмотра результата; effort не гарантирует качество ассетов.
- Фиксировать кратко результат, проверки и оставшийся блокер. Переоценивать поздние задачи по фактическим результатам, не планировать весь проект заново.

## 4. Задачи, зависимости и критерии готовности

Все задачи ниже запланированы, выполнение не подтверждено. P0 — ближайший приоритет; P1 — после проверки первой смены; P2 — после подтверждения интереса к продолжению.

### Этап 1. Проверить FIRST DEAL — P0

| ID | Задача | Effort агента | Результат |
| --- | --- | --- | --- |
| G1 | Подготовить маршруты и форму наблюдений | low | Фиксируются покупка, тест, продажа, помощь, выбор маршрута и итог |
| G2 | Провести 3–5 наблюдаемых прохождений | low | Записаны действия, затруднения, понимание ремонта и желание повторить |
| G3 | Разобрать результаты и выбрать исправления | medium | Отделены дефекты, проблемы понимания и предпочтения игроков |

Проверить также стартовый фокус управления, маленькое окно, паузу у дедлайна и клавиатурную навигацию. Первый проход — только с игровыми инструкциями, без устных подсказок. Повторные попытки использовать для маршрутов A/выкуп, A+Б/ремонт, Б/повтор, пропуск сроков и отказ.

Критерий перехода: есть наблюдаемые результаты и список препятствий; после исправлений игрок способен самостоятельно завершить смену и объяснить изменение денег. Выборка качественная и не доказывает статистически баланс или интересность.

### Этап 2. Улучшить интерфейс — P0

| ID | Задача | Effort агента | Результат |
| --- | --- | --- | --- |
| U1 | Сократить HUD и дозировать обучение | medium | Постоянно видны деньги, время, цель и переносимый предмет; детали появляются по ситуации |
| U2 | Разделить предложения на карточки и уточнить отказы | medium | Видны количество, требования, оплата, срок, статус и причина недоступности |
| U3 | Проверить меню, фокус и размеры окна | medium | Клавиатура, Escape, пауза и текст работают на выбранных размерах без перекрытий |

Зависимость: G3 определяет конкретные изменения; правила торговли сохраняются. Критерий: повторное наблюдение подтверждает устранение найденных препятствий, а информация не закрывает значимую часть мира.

### Этап 3. Оформить мастерскую и торговый двор — P1

| ID | Задача | Effort агента | Результат |
| --- | --- | --- | --- |
| V1 | Уточнить масштаб, маршруты и визуальные ориентиры | medium | Мастерская, выход, продавец и покупатели различимы по окружению |
| V2 | Сделать основные модели и материалы | medium | Согласованные фонарь, ящик, батарея, верстак и прибор проверки |
| V3 | Настроить свет и окружение | medium | Читаемое рабочее место, различимые помещение и двор, умеренные детали |
| V4 | Оформить условных персонажей и проверить интеграцию | medium | Простые позы/реакции, верный масштаб, доступные взаимодействия и проходы |

Зависимости: D3, этап 2. Объём предполагает простые модели без сложного рига, озвученных диалогов и лицевой анимации. Цветовые ориентиры дополняются формой, подписью и значком. Критерий: один участок показывает целевой облик игры; новые ассеты не ухудшают управление, видимость и производительность на выбранном тестовом ПК.

### Этап 4. Звук и ощущение действий — P1

| ID | Задача | Effort агента | Результат |
| --- | --- | --- | --- |
| F1 | Добавить звук основных действий и фон локации | low | Различимы покупка, контакт предметов, тест, ремонт, продажа и предупреждение |
| F2 | Добавить короткие движения и визуальные реакции | medium | Понятны взятие/укладка, проверка, затрата времени на ремонт и передача товара |
| F3 | Проверить совместную подачу сигналов | medium | Нет мешающих повторов, задержек и зависимости понимания только от звука или цвета |

Зависимости: стабильные взаимодействия этапа 2, основные ассеты этапа 3. Критерий: игрок замечает результат действия; эффекты не мешают управлению и соблюдают паузу.

### Этап 5. Вторая смена и сохранение — P2

| ID | Задача | Effort агента | Результат |
| --- | --- | --- | --- |
| S1 | Спроектировать вторую ситуацию с фонарями | medium | Другая партия/предложения создают выбор быстрого дохода и вложения в ремонт |
| S2 | Реализовать минимальное сохранение и загрузку | high | Деньги, предметы и переход между сменами восстанавливаются; сбой загрузки обрабатывается |
| S3 | Добавить данные второй смены и переход | medium | Начало следующей смены учитывает согласованные результаты первой |
| S4 | Проверить маршруты и желание продолжать | high | Нет потерь/дублирования; записаны причины выбора и интерес к следующей смене |

Зависимости: этапы 1–4, D1 и D2; новые правила отдельно согласуются с владельцем. Критерий: игрок проходит две смены, сохранение восстанавливает состояние, решения меняются по обстоятельствам. Если повторение неинтересно, сначала переработать ситуацию, затем переходить к прогрессии.

### Этап 6. Одно улучшение мастерской — P2

| ID | Задача | Effort агента | Результат |
| --- | --- | --- | --- |
| P1 | Выбрать улучшение и стоимость | medium | Заработок открывает новый способ действовать; например, второе место или прибор |
| P2 | Реализовать покупку, эффект и сохранение | medium | Улучшение влияет на работу, корректно покупается и восстанавливается |

Зависимость: подтверждённая польза второй смены и сохранения. Критерий: улучшение меняет действия, а не только число дохода. План включает одно выбранное улучшение, а не дерево развития.

### Этап 7. Второй товар — P2

| ID | Задача | Effort агента | Результат |
| --- | --- | --- | --- |
| C1 | Определить новую проверку/решение для товара | medium | Товар отличается поведением и риском, а не только ценой и моделью |
| C2 | Минимально расширить модель предметов и данные заказов | high | Есть одна власть над владением, перемещением, состоянием и продажей; выбран путь для старого инвентаря |
| C3 | Интегрировать товар, проверку и сделки | medium | Простой ассет и поведение работают в существующей локации и сохранениях |
| C4 | Проверить экономику, регрессии и прохождение | high | Старые маршруты сохранены; нет повторных выплат, потерь и дублирования |

Зависимости: этапы 5–6 и обновлённые правила. Перед реализацией уточнить товар, effort и объём: сложная разборка или отдельная мини-игра в текущий объём не входят. Критерий: новый товар добавляет осмысленное решение без переписывания всего цикла.

## 5. Порядок запуска и ближайший пакет

| Этап | Рекомендуемый effort |
| --- | --- |
| 1. Плейтест FIRST DEAL | low для подготовки/сбора; medium для выводов |
| 2. Интерфейс и обучение | medium |
| 3. Визуал мастерской и двора | medium |
| 4. Звук и ощущение действий | low для подключения звука; medium для интеграции |
| 5. Вторая смена и сохранения | medium; high только S2 и S4 |
| 6. Одно улучшение мастерской | medium |
| 7. Второй товар | medium; high только C2 и C4 |
| Документация | low для актуализации; medium для формулирования правил |

Первый пакет: G1 → G2 → G3 → U1–U3, затем D1 и обновление D4. Не выполнять его одним большим запуском: сначала получить результаты игроков, затем выбрать конкретные исправления. Визуальную работу начать с D3, затем V1 и основных предметов V2. Настройки для отдельных задач указаны в таблицах выше.

Это план ограниченного игрового фрагмента, не всей игры и не готовности к релизу. Трудозатраты в днях и календарные обещания не используются.

Не менять баланс без наблюдений: сейчас A с выкупом неисправного остатка даёт $415, A+Б с ремонтом — $455. Ремонт только ради выкупа уменьшает деньги на $25: батарея стоит $50, увеличение выкупа — $25. Проверить, понимает ли игрок этот выбор.

## 6. Технические условия выполнения

- Сохранять версию Unity, пакеты, GUID и ссылки сцен. Не смешивать задачи с миграцией.
- Расширять существующую модель по доказанной необходимости: предметы перед ассортиментом, данные заказов перед ростом сценариев, сохранения перед прогрессией. Не вводить новый каркас архитектуры заранее.
- Для каждой реализации проводить подходящие узкие проверки: diff, компиляция, затронутые редакторские сценарии, ручная проверка изменённых действий. Для экономики проверять атомарность, сроки, идентичности и однократность оплаты.
- После визуальных изменений наблюдать читаемость и измерять производительность на явно записанном оборудовании/разрешении; целевой бюджет определить до приёмки.
- Сборку Player, чистое воспроизведение проекта и подготовку релиза оценивать отдельно при соответствующей задаче. Архивы и пакеты по этому плану автоматически не создавать.
