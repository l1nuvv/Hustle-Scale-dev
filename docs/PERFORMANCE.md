# Производительность: аудит 22.10.2026

## A. Результат и границы

Подтверждена и устранена одна причина задержек торгового интерфейса: `CityTradeView.Execute` пересоздавал всё меню после каждого синхронного события модели и ещё раз после команды. Успешная покупка строила меню четыре раза, отказ — три. Теперь промежуточные события продолжают обновлять мир и HUD, а меню строится один раз после окончательного состояния команды.

В двух Development Player-прогонах на сторону средняя синхронная покупка ускорилась с **13,43 до 4,05 мс**, средний GC всего кадра покупки снизился с **1 720 563 до 478 947 B**. Это измерение конкретной операции; увеличение обычного FPS не заявляется. Проверены действующие FIRST DEAL, городские правила, архитектура, инженерный стандарт, workflow, roadmap и прежний профиль E5.8. E6.6 остаётся человеческой приёмкой.

Аудит включает статический поиск горячих API в 50 runtime C#-файлах (один сгенерированный), чтение критических путей, семь игровых сцен, реальные Player-измерения, Editor Frame Timing/Frame Debugger и доступные регрессионные harness. GPU Player, холодный запуск до управления, длительный memory soak и полный профиль видимого обычного Player не измерены. Отсутствие таких данных не означает отсутствие проблем.

## C. Baseline и обычный кадр

Каждый стационарный прогон: продавец, двор, мастерская, A, меню A/150%, указатели, пауза/150%; **3 с прогрева + 8 с выборки на станцию**, 56 с измеряемых кадров, около 80 с на процесс. Сравниваются `baseline-2`, `baseline-3` и `after-1`, `after-2`. `baseline-1` оставлен только как диагностический: в начале переключался Editor Play Mode, поэтому этот прогон исключён из сравнения.

Подробные frame p50/p95/p99/max, Main Thread, render submit, GC и station-end memory находятся в `profile.json` каждого прогона. Main Thread включает ожидания; CPU render submit входит в работу главного потока. Их нельзя складывать друг с другом или с GPU. Загрузочные/снимочные кадры вне стационарного окна не доказывают отсутствие first-use hitches.

## D. CPU и горячие пути

Основной подтверждённый расход — `CityTradeUI.RebuildMenu`: создание Text/Button/Layout/Image, пересборка Canvas и отложенное уничтожение старых дочерних объектов. `SetPaused(false)` → `Changed`, успешная модельная команда → `Changed`, `SetPaused(true)` → `Changed`, финальный `Refresh` запускали четыре полные перестройки. Отказ также создавал три версии. Наблюдение идентичности контролов в Editor подтвердило последовательность; Player подтвердил стоимость.

Обычные пути: CharacterController и камера выполняют необходимое движение каждый кадр; PlayerRaycast делает один nearest-hit запрос и отдельный запрос при E; машина — четыре WheelCollider в FixedUpdate и обновление визуальных колёс в LateUpdate. Глобальные поиски в CityTradeWayfinding, создании мира и legacy setup относятся преимущественно к запуску/смене режима. Доказательств, что эти редкие поиски ограничивают обычный кадр, не получено. Удалять их или вводить общий кеш/пул без измерения не требуется.

Из сохранённого CPU Profiler capture `editor-baseline.raw` разобраны 79 кадров главного потока: индексы 100..1660 с шагом 20, без краёв записи. Среднее inclusive-время каждого маркера на выбранный кадр:

| Маркер | мс/кадр |
| --- | ---: |
| Physics.Simulate | 0,1136 |
| Canvas.SendWillRenderCanvases | 0,0340 |
| CityUtilityVehicle.FixedUpdate | 0,0157 |
| CityUtilityVehicle.LateUpdate | 0,0100 |
| CityTradeView.LateUpdate | 0,0067 |
| CityUtilityVehicle.Update | 0,0032 |
| PlayerController.LateUpdate | 0,0021 |
| CitySaveController.Update | 0,0019 |
| PlayerRaycast.Update | 0,0010 |

Физический маркер включает симуляцию мира; FixedUpdate может вызываться ноль или несколько раз на кадр. Inclusive-маркеры нельзя суммировать как независимые интервалы. Это выборка текущего спокойного Editor-состояния с allocation callstacks, не Deep Profile, не стоимость торгового действия/активного вождения и не замена Player-цифрам. Полная выборка — `editor-cpu-markers.csv`. Доказанного steady-state CPU bottleneck среди этих callbacks нет.

## F. Memory и GC

`baseline-2`: Unity allocated 144,93–146,08 MiB, reserved 545,19–547,19 MiB, managed used 3,09–4,45 MiB в концах станций. Это не пики working set, VRAM или доказательство утечки. Диагностический Editor-снимок существенно больше: allocated 763,11 MB, reserved 2050,38 MB, mono used 60,32 MB; не сравнивать с Player.

Штатный GC counter доступен. API `GC.GetAllocatedBytesForCurrentThread` в этом Editor возвращает нули даже после явной аллокации; эти нули отклонены. Маркер `GC.Alloc` также проверен: единицы TimeNanoseconds, поэтому его CurrentValue нельзя использовать как байты. Для таблицы команд используется `GC Allocated In Frame` следующего кадра — полные байты кадра действия, включая отложенную UI-работу, autosave и фоновые расходы, а не только Execute.

Уничтожение UI artwork, материалов, RenderTexture, audio clips и подписок прослежено по lifecycle; повторное восстановление проверено E5.7/E6. Рост managed used между станциями сам по себе не классифицируется как leak. Memory Profiler package не установлен, новый пакет не добавлялся. Сравнительных heap snapshots и многочасового soak нет.

## G. Загрузка и задержки

Player запускается и проходит профили; длительность station-процесса включает 77 с запрограммированного прогрева/выборки, PNG и завершение. Вычитать 77 с и называть остаток startup нельзя. Холодный process-launch → first frame/control, scene activation, отдельное появление NPC и первое использование ресурса не инструментированы; отдельных достоверных значений нет. Editor import не выдаётся за Player startup.

Поддержанные гипотезы для следующего измерения: синхронное построение мира/знаков, генерация трёх UI текстур (77 824 SetPixel-вызова при создании), синтез audio clips, JsonUtility/SHA-256/Flush сохранения. Их частота — запуск, новое меню или транзакция; bottleneck для каждой отдельно не подтверждён. Не добавлены Addressables, preload-система или асинхронная запись без измерения и отдельной проверки атомарности.

## H. Время и физика

Городские часы продвигает CitySaveController через Time.deltaTime, FIRST DEAL — FirstDealView; пауза/меню/потеря фокуса не продвигают активные часы. Модель проверяет конечные неотрицательные интервалы, дедлайн сравнивается точно через `>=`, ремонт прибавляет прежние 240 с. Движение умножается на deltaTime; mouse delta уже покадровая и повторно не масштабируется. Fixed timestep 0,02 с, maximum allowed timestep 0,33333334 с; параметры не менялись. При экстремальной остановке кадра deltaTime ограничивается движком — отдельный сценарий длительного зависания не измерен.

Reach 2,5 м, блокировка стеной/ближайшим hit, query masks, управление, collision layers и доступность предметов сохранены. Точная проверка FPS-independent wall-clock при 30/60/144 FPS в реальном Player не выполнена; исходники и детерминированные проверки не подменяют такой эксперимент.

## I. Качество кода и масштабирование

WorkshopSession остаётся владельцем экземпляров/денег/заказов. Проверки группы и выплаты атомарны; invalid/repeated IDs не превращены в ускоренные обходы валидации. Изменён только момент обновления меню внутри синхронной команды, без новых событий, контейнеров или менеджеров.

Текущая нагрузка ограничена тремя активными экземплярами, двумя городскими партиями и фиксированными заказами; NPC стоят на местах, самостоятельного NPC AI нет. 128 RNG seeds/две партии, 64×256 модельных действий, повторные покупки/отказы/загрузки и 9 перезапусков command-последовательности — ограниченная проверка текущего масштаба. Она не доказывает поддержку 100–500 товаров/NPC. Генерализация коллекций, pooling и DOTS без нового контракта не обоснованы.
